# Техническое задание: кинотрекер для клуба кинолюбителей

Версия ТЗ: 1.1. Дата: 24 октября 2026 года.

## 1. Назначение проекта

Разработать бэкенд на Python и FastAPI для одного закрытого клуба кинолюбителей. Участники находят фильмы, добавляют их в каталог клуба, выставляют оценки по категориям, оставляют анонимные для других участников отзывы и сравнивают мнение клуба с внешними рейтингами.

Результат работы — REST API с документацией Swagger, базой данных, автоматическими тестами, CI в GitHub Actions и инструкциями в публичном репозитории GitHub. Основные сценарии должны выполняться через Swagger без отдельного интерфейса.

## 2. Границы первой версии и принятые правила

- Приложение обслуживает один клуб. Все зарегистрированные участники имеют одинаковые права на фильмы и собственные отзывы и оценки.
- Регистрация доступна по одноразовому приглашению. Приглашения создаёт организатор клуба командой приложения на сервере; отдельная административная панель не требуется.
- Каталог, отзывы и рейтинги клуба доступны после входа. Анонимность означает отсутствие имени автора в ответах для других участников, а доступ сохраняется только у членов клуба.
- Участник может оставить оценки, текстовый отзыв или оба вида обратной связи. На пару «участник — фильм» существует одна изменяемая запись.
- Участник отдельно оценивает шесть параметров: идею, сюжет, сценарий, игру актёров, звук и визуал. Общая оценка рассчитывается сервером как средняя взвешенная; в первой версии веса всех параметров равны 1.
- Сведения о фильмах загружаются из внешнего API, а клубные оценки и отзывы хранятся в собственной базе.
- Подбор фильмов в первой версии реализуется через поиск, фильтры и сортировку. Персональные алгоритмы рекомендаций, несколько клубов и история изменений могут быть добавлены позднее.

## 3. Регистрация, вход и восстановление пароля

### 3.1. Регистрация по приглашению

1. Организатор создаёт приглашение для конкретного email через CLI приложения. Команда и пример её выполнения описаны в README.
2. Приложение генерирует случайный одноразовый код со сроком действия 7 дней и показывает его организатору один раз. В базе сохраняется хеш кода.
3. Пользователь передаёт email, пароль и код приглашения в запросе регистрации.
4. Приложение проверяет код, срок действия, совпадение email и отсутствие зарегистрированного пользователя с этим адресом.
5. Создание пользователя и погашение приглашения выполняются в одной транзакции. Одно приглашение нельзя использовать дважды, включая одновременные запросы.

Email нормализуется одинаково при регистрации, входе и восстановлении: удаляются пробелы по краям и приводятся к нижнему регистру. Нормализованный email уникален. Пароль — от 12 до 128 символов; пробелы и регистр пароля сохраняются. Email и пароль проверяются на сервере.

### 3.2. Вход и проверка доступа

- Вход выполняется по email и паролю. При ошибке возвращается одинаковое сообщение о неверных учётных данных.
- Успешный вход возвращает JWT access token, `token_type: bearer` и срок его действия. Срок по умолчанию — 30 минут, он задаётся настройкой.
- Защищённые запросы передают `Authorization: Bearer <token>`.
- Сервер проверяет подпись с фиксированным разрешённым алгоритмом, срок действия, идентификатор пользователя и версию авторизации `auth_version`.
- В базе хранится только Argon2-хеш пароля. Пароли и токены не возвращаются в профиле и не попадают в логи.

JWT и Argon2 выбраны по подходу из [документации FastAPI по безопасности](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/). Конкретные сроки действия являются требованиями этого проекта.

### 3.3. Восстановление пароля

1. Пользователь отправляет email в запросе восстановления.
2. Для корректного по формату адреса сервер возвращает `202` и одинаковое сообщение: «Если аккаунт существует, инструкция отправлена на почту». Ответ не должен позволять определить наличие аккаунта; отправка письма не должна создавать явную разницу во времени ответа.
3. Для существующего пользователя создаётся криптографически случайный одноразовый токен со сроком действия 30 минут. В базе хранится только его хеш. Предыдущий токен этого пользователя аннулируется.
4. Токен отправляется на зарегистрированный email через SMTP. Для проверки без фронтенда пользователь может перенести токен из письма в запрос Swagger.
5. Запрос подтверждения содержит токен и новый пароль. После проверки сервер атомарно меняет хеш пароля, погашает все токены восстановления пользователя и увеличивает `auth_version`.
6. Все ранее выданные JWT пользователя становятся недействительными. Для продолжения работы необходимо войти с новым паролем.

Токен восстановления не возвращается в HTTP-ответе и не записывается в логи. В локальной разработке письма проверяются через тестовый SMTP-сервер с просмотром писем; в автотестах отправщик подменяется. Ошибка доставки фиксируется в логе без email и содержимого письма; пользователю остаётся доступен повторный запрос.

Защита от частых запросов обязательна: вход — до 10 попыток за 10 минут на IP; восстановление — до 5 запросов в час на IP и не более одного письма в минуту на нормализованный email. Подавление повторного письма не меняет нейтральный ответ. Для одного процесса допустим лимитер в памяти; ограничение такого решения описывается в README.

Требования к нейтральному ответу, одноразовости токенов и аннулированию сессий основаны на [рекомендациях OWASP по восстановлению пароля](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## 4. Фильмы, поиск и подбор

### 4.1. Сведения о фильме

Карточка содержит внутренний `id`, уникальный `kinopoisk_id`, названия, год, описание, жанры, страны, продолжительность, ссылку на постер, актёров и режиссёров. Отсутствующие у источника значения сохраняются как `null` или пустые списки. Для съёмочной группы сохраняются идентификатор источника, имя, профессия и роль при наличии.

Также возвращаются средние клубные оценки, количество оценивших участников, количество отзывов, внешние рейтинги и время последнего успешного обновления внешних данных.

### 4.2. Поиск во внешнем каталоге

Участник может искать фильмы по названию и подбирать их по жанру, стране, диапазону лет и внешнему рейтингу. API проекта принимает собственные понятные параметры и преобразует их в запрос провайдеру.

Параметры: `query`, `genre_id`, `country_id`, `year_from`, `year_to`, `rating_from`, `rating_to`, `sort`, `page`. В первой версии выбирается один жанр и одна страна. Диапазоны проверяются: нижняя граница не больше верхней, рейтинг — от 0 до 10. Каталог ограничивается фильмами типа `FILM` у провайдера.

Допустимые сортировки внешнего поиска: `rating_desc`, `votes_desc`, `year_desc`. Фильтры необязательны. Результат содержит краткие карточки с `kinopoisk_id`, номер страницы и доступное количество страниц; ограничение глубины поиска провайдера отражается в документации собственного API.

### 4.3. Каталог клуба

Участник добавляет найденный фильм по `kinopoisk_id`. Сервер загружает сведения из внешнего API и сохраняет локальную карточку. Повторное добавление того же фильма возвращает существующую карточку и не создаёт дубликат, в том числе при одновременных запросах.

Локальный каталог поддерживает поиск по названию, фильтры `genre_id`, `year_from`, `year_to`, `club_rating_from`, `min_votes` и сортировки `title_asc`, `year_desc`, `club_rating_desc`. Фильтр `club_rating_from` использует клубную общую оценку. При сортировке по рейтингу фильмы без голосов идут в конце; равные значения упорядочиваются по внутреннему `id`.

Списки локальных фильмов и отзывов используют `page` и `page_size`: по умолчанию 1 и 20, максимум 100 элементов на страницу. Ответ содержит `items`, `total`, `page`, `page_size`. Поиск по названию не учитывает регистр. Страница после конца списка возвращает пустой `items`.

## 5. Оценки, отзывы и статистика

### 5.1. Категории оценивания

| Поле API | Категория | Допустимые значения |
|---|---|---|
| `idea` | Идея | Целое число 1–10 |
| `plot` | Сюжет | Целое число 1–10 |
| `screenplay` | Сценарий | Целое число 1–10 |
| `acting` | Игра актёров | Целое число 1–10 |
| `sound` | Звук | Целое число 1–10 |
| `visuals` | Визуал | Целое число 1–10 |

Если участник выставляет оценки, он заполняет все шесть параметров. Дробные числа, булевы значения и числа вне диапазона отклоняются. Общая оценка `overall` рассчитывается сервером и возвращается в ответах; клиент не может передавать её или веса в запросе сохранения оценок. Такие поля отклоняются с `422`.

Формула общей оценки участника:

```text
overall = (idea * w_idea + plot * w_plot + screenplay * w_screenplay
           + acting * w_acting + sound * w_sound + visuals * w_visuals)
          / (w_idea + w_plot + w_screenplay + w_acting + w_sound + w_visuals)
```

В первой версии все шесть весов равны 1, поэтому формула принимает вид:

```text
overall = (idea + plot + screenplay + acting + sound + visuals) / 6
```

Веса едины для всех участников и фильмов и задаются конфигурацией сервера. Каждый вес — конечное положительное число; набор должен содержать ровно шесть перечисленных параметров. Если впоследствии веса изменятся, после перезапуска сервера все производные оценки рассчитываются с новыми весами из сохранённых исходных оценок; количество голосов не меняется. Использованные веса возвращаются в статистике в поле `rating_weights`.

### 5.2. Собственная запись участника

В базе действует уникальное ограничение `(user_id, movie_id)`. Автор определяется по токену: передать или изменить `user_id` в запросе нельзя.

Тело записи содержит два поля: `scores` — объект с шестью оценками либо `null`; `review` — текст либо `null`. Хотя бы одно поле должно содержать данные. Текст после удаления пробелов по краям имеет длину от 1 до 5000 символов; пустой текст считается отсутствующим. Отзыв хранится и выдаётся как обычный текст.

Пример запроса:

```json
{
  "scores": {
    "idea": 9,
    "plot": 8,
    "screenplay": 9,
    "acting": 8,
    "sound": 10,
    "visuals": 9
  },
  "review": "Понравились атмосфера и музыка."
}
```

`PUT` создаёт или полностью заменяет собственную запись. Оба поля передаются явно: `null` удаляет соответствующую часть. Повторный одинаковый запрос не добавляет голосов. `DELETE` удаляет всю запись; чтобы убрать только отзыв или только оценки, используется `PUT` с сохранением второй части.

### 5.3. Средние оценки и счётчики

- `ratings_count` — число уникальных участников, у которых заполнен блок `scores`. Отзыв без оценок не увеличивает этот счётчик.
- Для каждого из шести параметров вычисляется арифметическое среднее: сумма текущих оценок параметра / `ratings_count`.
- Клубная общая оценка `overall` — арифметическое среднее неокруглённых общих оценок участников. При единых весах это также равно средней взвешенной шести средних оценок клуба. Все участники имеют одинаковый вес голоса.
- Значения округляются до двух знаков только при формировании ответа; сортировки и фильтры используют неокруглённое среднее.
- `reviews_count` — число записей с непустым текстом отзыва. Этот счётчик может отличаться от `ratings_count`.
- Если оценок нет, средние равны `null`, а `ratings_count` — 0. Отсутствие оценки не представляется нулём.
- Изменение или удаление записи отражается в статистике сразу после успешного завершения запроса.

Пример: если первый участник поставил 7 по каждому параметру, его общая оценка равна 7; если второй поставил везде 10, его общая оценка равна 10. Клуб получает `overall = 8.5`, `ratings_count = 2`. После удаления первой записи получаются `overall = 10.0`, `ratings_count = 1`. Для примера запроса выше при равных весах общая оценка равна `53 / 6`, в ответе — `8.83`.

Для небольшой базы статистика вычисляется по актуальным исходным оценкам, без отдельного фонового пересчёта. Производная общая оценка не хранится как независимое редактируемое значение. Отзыв без блока `scores` не имеет общей оценки.

### 5.4. Анонимные отзывы

Участник может последовательно получить все отзывы о фильме через пагинацию. В ответе на каждый отзыв возвращаются только случайный `review_id`, текст и дата создания; порядок — от новых к старым с дополнительным упорядочиванием по `review_id`.

В списке отсутствуют имя, email, `user_id`, ссылка на профиль и другие поля автора. Связь с пользователем хранится в базе для проверки прав. Владелец базы технически может определить автора; это не система абсолютной анонимности.

Собственную запись пользователь получает отдельным маршрутом `/feedback/me`. Чужую запись нельзя получить, изменить или удалить через этот маршрут.

## 6. Внешний API и сравнение рейтингов

Первый провайдер — **Kinopoisk Unofficial API**, то есть неофициальный сервис, а не официальный API Кинопоиска. Для доступа нужен ключ в заголовке `X-API-KEY`. На сайте для новых пользователей указан лимит 500 запросов в сутки; фактическую квоту необходимо проверять для используемого аккаунта. Источники: [Swagger провайдера](https://kinopoiskapiunofficial.tech/documentation/api/) и [сайт провайдера](https://kinopoiskapiunofficial.tech/).

Используемые методы провайдера:

| Метод | Назначение |
|---|---|
| `GET /api/v2.2/films` | Поиск и фильтры |
| `GET /api/v2.2/films/filters` | Справочники жанров и стран |
| `GET /api/v2.2/films/{id}` | Карточка и внешние рейтинги |
| `GET /api/v1/staff?filmId={id}` | Актёры и режиссёры |

Карточка источника предусматривает рейтинг Кинопоиска, рейтинг IMDb и их счётчики голосов; значения могут отсутствовать. Поиск ограничен 20 страницами по 20 фильмов; у метода поиска есть ограничение 5 запросов в секунду. Проверено по [OpenAPI-схеме провайдера](https://kinopoiskapiunofficial.tech/documentation/api/openapi.json) 24 октября 2026 года.

Требования к интеграции:

- Ключ используется только сервером и читается из окружения. В ответах собственного API и логах ключ отсутствует.
- Фильм сопоставляется по `kinopoisk_id`, а не по совпадению названий.
- Внешние рейтинги хранятся отдельно от клубных. С клубной общей оценкой сравниваются общие оценки источников; категории клуба не подменяются внешними данными.
- Для внешних оценок возвращаются название источника, значение, счётчик голосов при наличии и дата загрузки. Для IMDb указывается, что поставщик данных — Kinopoisk Unofficial API. Примеры чисел в документации проекта помечаются как условные.
- Адаптер провайдера отделяется от маршрутов и клубной логики, чтобы его можно было подменить в тестах или заменить другим провайдером.
- Карточки, съёмочная группа и рейтинги сохраняются в SQLite. Срок актуальности — 24 часа. При чтении устаревшей карточки сервер пытается обновить внешние сведения; успешное обновление не меняет клубные записи.
- Результаты внешнего поиска кэшируются на 10 минут по нормализованным параметрам; справочники — на 24 часа. Для одного процесса допустим кэш поиска в памяти.
- На запрос к провайдеру задаётся таймаут 5 секунд, автоматические повторы в первой версии не выполняются. При нескольких запросах на карточку общее ожидание ограничивается 10 секундами. Исходящие вызовы ограничиваются двумя запросами в секунду на процесс.
- При сбое обновления возвращается сохранённая карточка с `external_data_stale: true` и временем последней успешной загрузки. Неполный ответ не должен уничтожать ранее сохранённые данные.
- Если при первом импорте карточка получена, а съёмочная группа недоступна, фильм можно сохранить с `metadata_incomplete: true`; недостающие сведения загружаются при следующем обновлении.
- Если данных нет и источник недоступен, возвращается `503` с кодом `external_service_unavailable`. Если источник подтвердил отсутствие фильма — `404`. Исчерпание внешней квоты также обрабатывается как временная недоступность, а не как ошибка авторизации участника.
- При отсутствии ключа приложение запускается и работает с локальными фильмами, оценками и отзывами; внешние операции возвращают `503` с кодом `external_service_not_configured`.

## 7. Маршруты собственного API

Формат запросов и ответов — JSON. Служебные маршруты находятся в корне; остальные имеют префикс `/api/v1`. Все строки таблицы, кроме явно открытых, требуют Bearer-токен.

| Метод | Маршрут | Назначение и доступ |
|---|---|---|
| GET | `/health` | Открытый: проверить приложение и доступность БД |
| GET | `/version` | Открытый: получить версию приложения |
| POST | `/api/v1/auth/register` | Открытый: зарегистрироваться по приглашению |
| POST | `/api/v1/auth/login` | Открытый: получить токен по email и паролю |
| POST | `/api/v1/auth/forgot-password` | Открытый: запросить восстановление |
| POST | `/api/v1/auth/reset-password` | Открытый: установить пароль по токену восстановления |
| GET | `/api/v1/users/me` | Получить собственный профиль |
| GET | `/api/v1/catalog/films` | Найти или подобрать фильмы во внешнем каталоге |
| GET | `/api/v1/catalog/filters` | Получить жанры и страны |
| POST | `/api/v1/movies` | Добавить фильм в клуб по `kinopoisk_id` |
| GET | `/api/v1/movies` | Получить локальный каталог с фильтрами |
| GET | `/api/v1/movies/{movie_id}` | Получить карточку, средние оценки и внешние рейтинги |
| GET | `/api/v1/movies/{movie_id}/feedback/me` | Получить свою запись с оценками и отзывом |
| PUT | `/api/v1/movies/{movie_id}/feedback/me` | Создать или заменить свою запись |
| DELETE | `/api/v1/movies/{movie_id}/feedback/me` | Удалить свою запись |
| GET | `/api/v1/movies/{movie_id}/reviews` | Получить анонимные отзывы участников |

`movie_id` — внутренний положительный идентификатор. Он отличается от внешнего `kinopoisk_id`. При отсутствии фильма или собственной записи возвращается `404`. Пустой список отзывов существующего фильма возвращается с `200`.

Коды успешных ответов: чтение и вход — `200`; регистрация и создание фильма — `201`; повторное добавление фильма — `200`; `PUT` собственной записи — `200` с актуальной записью; удаление и успешный сброс пароля — `204`; запрос восстановления — `202`.

Ошибки: `401` — отсутствующий, неверный или истёкший access token; `409` — уже зарегистрированный email; `422` — некорректные поля, непригодное приглашение или токен восстановления; `429` — превышен локальный лимит запросов. Непредвиденная ошибка возвращает `500` без внутренних подробностей.

Ошибки имеют единый объект `error` с `code`, `message`, `request_id` и необязательным `details` для безопасного описания полей. Значения паролей, кодов и токенов не включаются даже в ошибки валидации.

`GET /health` выполняет простую проверку БД: при успехе — `200` и `{"status":"ok","database":"ok"}`, при недоступной БД — `503` и нейтральное описание состояния. Внешний кино API и SMTP не определяют результат этой проверки.

`GET /version` возвращает `{"version":"0.1.0"}` с фактической версией текущего запуска. `/docs` предоставляет Swagger UI с описаниями схем, параметров, авторизации и ошибок.

## 8. Данные и ограничения базы

| Сущность | Основные поля |
|---|---|
| `User` | `id`, уникальный нормализованный `email`, `password_hash`, `auth_version`, `created_at` |
| `Invitation` | `id`, `email`, `token_hash`, `expires_at`, `used_at` |
| `PasswordResetToken` | `id`, `user_id`, `token_hash`, `expires_at`, `used_at` |
| `Movie` | `id`, уникальный `kinopoisk_id`, сведения о фильме, съёмочная группа, внешние рейтинги, `external_updated_at`, признаки неполноты и устаревания |
| `Feedback` | случайный UUID `id`, `user_id`, `movie_id`, шесть исходных оценок либо отсутствие всего блока, `review`, `created_at`, `updated_at`; общая оценка вычисляется при чтении |

Обязательны внешние ключи, уникальность `(user_id, movie_id)` и проверка диапазонов оценок. SQLite должен работать с включённой проверкой внешних ключей. Время хранится в UTC и выдаётся в ISO 8601. Миграции схемы включаются в репозиторий.

Для небольшой первой версии списки жанров, стран, участников съёмочной группы и внешние снимки рейтингов допустимо хранить в JSON-полях карточки. Фильтры по этим данным должны работать на выбранной SQLite, что проверяется интеграционными тестами.

## 9. Техническая реализация и настройки

Базовый стек: Python 3.12, FastAPI, Uvicorn, Pydantic, SQLAlchemy, SQLite, Alembic, HTTPX, PyJWT и библиотека для Argon2-хеширования. Тесты — pytest; проверка стиля — Ruff. Версии зависимостей фиксируются в выбранном файле зависимостей или lock-файле.

Код разделяется на маршруты, схемы запросов и ответов, модели БД, бизнес-логику, работу с провайдером, отправку писем и конфигурацию. Приложение разворачивается одним сервисом с одним рабочим процессом; это соответствует кэшу и лимитеру в памяти.

Настройки читаются из переменных окружения. Для локального запуска допускается настоящий `.env`, исключённый из Git. В репозитории находится только `.env.example` с названиями переменных и безопасными примерами.

| Настройка | Назначение |
|---|---|
| `APP_ENV` | `development`, `test` или `production` |
| `APP_VERSION` | Версия для `/version` и стартового лога |
| `DATABASE_URL` | Подключение к SQLite; пример — `sqlite:///./data/cinema.db` |
| `LOG_LEVEL` | Уровень логирования |
| `JWT_SECRET` | Обязательный случайный секрет подписи без встроенного рабочего значения |
| `ACCESS_TOKEN_TTL_MINUTES` | Срок access token, по умолчанию 30 минут |
| `RATING_WEIGHTS` | JSON-объект весов; по умолчанию `{"idea":1,"plot":1,"screenplay":1,"acting":1,"sound":1,"visuals":1}` |
| `KINOPOISK_API_KEY` | Ключ внешнего API |
| `EXTERNAL_CACHE_TTL_SECONDS` | Актуальность карточки и рейтингов, по умолчанию 86400 |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TLS` | Настройки отправки писем; локальный тестовый SMTP может работать без учётных данных |

Корректно настроенный сервис запускается и продолжает обслуживать запросы. Ошибки настроек диагностируются понятным сообщением без значений секретов. При публикации сервиса с реальными аккаунтами авторизация и запросы восстановления передаются через HTTPS.

## 10. Логи и диагностика

В стандартный вывод записываются запуск и завершение приложения, версия, метод и путь запроса без query string, HTTP-статус, длительность и `request_id`. Для изменяющих операций фиксируются тип события и `movie_id`, без текста отзыва и связи автора с отзывом в общем журнале запросов.

Также фиксируются ошибки БД, таймауты провайдера, исчерпание внешней квоты, результат обновления карточки и ошибки доставки писем. Внутренние исключения доступны в серверных логах, но их контекст очищается от секретов.

Запрещено логировать пароли, access token, приглашения, токены восстановления, заголовки авторизации, API-ключи, SMTP-пароли, тела писем и запросов авторизации. Для внешних HTTP-клиентов исключается отладочный вывод чувствительных заголовков.

## 11. Автоматические тесты и CI

Тесты запускаются одной командой и используют изолированную временную SQLite. Внешний кино API и SMTP подменяются управляемыми тестовыми реализациями: настоящие ключи, интернет и отправка писем для тестов не требуются.

Обязательные группы проверок:

1. **Запуск:** приложение создаётся, `/health` и `/version` возвращают ожидаемые ответы; недоступная БД корректно отражается в `/health`.
2. **Регистрация и вход:** корректное приглашение, повторное использование, другой email и истечение срока; верный и неверный пароль; закрытый маршрут без токена; истёкший или подделанный токен.
3. **Восстановление:** нейтральный ответ для существующего и отсутствующего email; письмо через подменённый отправщик; истёкший и повторно использованный токен; новый пароль работает, старый пароль и прежние JWT — нет; проверка лимитов запросов.
4. **Фильмы:** импорт, сохранение после перезапуска, отсутствие дублей, локальный и внешний поиск, фильтры, сортировка, пагинация, неизвестный идентификатор.
5. **Оценки:** все шесть параметров; отклонение значений 0, 11, дробей, булевых значений и неполного блока; запрет передавать `overall` и веса; правильная средняя взвешенная при равных и неравных тестовых весах; клубная общая оценка без промежуточного округления; валидация конфигурации весов; пересчёт при смене весов без изменения голосов; правильные средние по параметрам и счётчики; повторный `PUT`; изменение и удаление; `null` при отсутствии голосов.
6. **Отзывы и права:** отзыв без оценок; оценки без текста; пустая запись отклоняется; собственная запись редактируется; другой пользователь не изменяет её; в списке отзывов отсутствуют поля автора; через пагинацию доступны все отзывы.
7. **Интеграция:** кэш уменьшает число обращений к провайдеру; таймаут, квота, неверный ключ и отсутствие внешнего рейтинга обрабатываются; сохранённые данные возвращаются при сбое; отсутствие API-ключа не мешает локальным операциям.
8. **Ограничения БД и приватность:** проверка уникальности фильма и обратной связи; токены и пароли не попадают в ответы ошибок и логи.

GitHub Actions запускается при `push` и `pull_request`: устанавливает Python и зависимости, запускает Ruff, применяет миграции к временной БД и выполняет pytest. Любой провал завершает проверку с ошибкой. CI не использует настоящие SMTP-данные и ключ провайдера.

## 13. Критерии приёмки

Проект считается выполненным, если:

- После клонирования и выполнения инструкций README сервис запускается без аварийного завершения и сохраняет данные после перезапуска.
- `/health` и `/version` работают; полезные маршруты и параметры доступны в Swagger.
- Посторонний пользователь не получает каталог, оценки и отзывы клуба; участник может зарегистрироваться по приглашению, войти и восстановить пароль.
- Поиск и подбор используют внешний API; добавленный фильм содержит доступные описание, актёров и режиссёров.
- Два разных участника могут оценить один фильм отдельно по идее, сюжету, сценарию, игре актёров, звуку и визуалу; средние по шести параметрам и число оценивших вычисляются правильно.
- Общая оценка вычисляется сервером как средняя взвешенная исходных оценок; при равных весах первой версии — как их сумма, делённая на 6. Клубная общая оценка вычисляется по всем участникам без промежуточного округления.
- Повторное сохранение своей записи не увеличивает число голосовавших; изменение и удаление корректно меняют статистику.
- Отзывы можно получить полностью через страницы; ответы для других участников не раскрывают автора.
- Можно оставить только текст или только оценки; счётчики отражают выбранный вариант.
- В карточке видны внешние и клубные рейтинги с понятными источниками и свежестью данных. Отсутствующие значения не заменяются нулями.
- Сбой провайдера не мешает читать сохранённые фильмы, оставлять оценки и отзывы.
- Как минимум `LOG_LEVEL` реально меняет поведение приложения через переменную окружения; прочие перечисленные настройки также используются по назначению.
- Основные события выводятся в лог без секретов и содержания приватных запросов.
- Автоматические тесты и проверки GitHub Actions проходят; тесты выполняются без настоящих ключей и внешней сети.
- Репозиторий публичный, README воспроизводим, настоящие `.env`, токены и пользовательские данные не опубликованы.

Рекомендуемый порядок реализации: каркас и БД → регистрация и вход → локальные фильмы и обратная связь → агрегаты и анонимные отзывы → внешний поиск и кэш → восстановление пароля → итоговая проверка README. Тесты и CI добавляются с первого этапа и дополняются вместе с функциями.
